# zenblitz

ZenVM is a C++ register-based virtual machine (computed-goto dispatch,
tri-color GC, fibers and cooperative processes, compact 32-bit bytecode).
The language it compiles is **Blitz Basic** (Blitz3D syntax): the compiler
front-end is a port of the original Blitz3D compiler (zlib licence) with the
x86 back-end replaced by a Zen bytecode emitter.

The runtime is the Zen VM reduced to what Blitz needs: register machine with
computed-goto dispatch, tri-color GC, interned strings, arrays, typed buffers
(banks), plain record types, bytecode dump/load. Fibers, processes, classes,
closures, maps, sets and the Zen builtin modules were removed (about 10 000
lines of core, down from 28 000). The interpreter can suspend at a native
call (`VM::request_suspend`) and continue later, which is how a Blitz main
loop will yield to the browser on the web build.

## Example

```blitz
Type Ball
	Field x#, y#, vy#
End Type

Function Spawn.Ball(x#, y#)
	b.Ball = New Ball
	b\x = x : b\y = y
	Return b
End Function

For i = 1 To 3
	Spawn(i * 100, 0)
Next

For b.Ball = Each Ball
	b\vy = b\vy + 0.5
	b\y = b\y + b\vy
	Print "ball " + b\x + "," + b\y
Next
```

## Building

```bash
cmake -S . -B build
cmake --build build -j
./bin/zenblitz program.bb
./bin/zenblitz --dis program.bb      # disassemble the generated bytecode
./bin/zenblitz -e 'Print "hi"'
```

## Tests

```bash
tests/run_tests.sh ./bin/zenblitz            # snapshot suite (tests/*.bb)
tests/run_tests.sh ./bin/zenblitz --update   # refresh tests/expected/*.out
```

The old Zen-syntax test-suite is kept in `tests/legacy_zen/` for reference.

## What is implemented

- Statements: `If/ElseIf/Else`, `While/Wend`, `Repeat/Until/Forever`,
  `For/Next` (int and float, `Step`), `For Each`, `Select/Case/Default`,
  `Exit`, `Goto`, `Gosub/Return`, `Include`, `Data/Read/Restore`, `End`.
- Declarations: `Global`, `Local`, `Const`, `Dim` (multi-dimensional),
  Blitz arrays (`Local a[10]`, `Field a[10]`), `Function` with default
  parameters and typed returns (`%`, `#`, `$`, `.Type`).
- Types: `Type/Field/End Type`, `New`, `Delete`, `Delete Each`, `First`,
  `Last`, `After`, `Before`, `Insert ... Before/After`, `Handle`, `Object.T`,
  `Null` semantics (deleted objects compare equal to `Null`).
- Expressions: Blitz precedence, `And/Or/Xor/Not`, `Shl/Shr/Sar`, `Mod`, `^`,
  automatic int/float/string conversion, `Int()`, `Float()`, `Str()`,
  Blitz float formatting (`1.5`, `10.0`, `0.333333`).
- Commands (console subset): `Print`, `Write`, `Input`, string commands
  (`Left`, `Mid`, `Instr`, `Replace`, `Hex`, ...), maths (`Sin` in degrees,
  `Rnd/Rand` with Blitz's own generator, ...), `MilliSecs`, `Delay`,
  `CommandLine`, timers, `RuntimeError`.
- Files and banks: `OpenFile/ReadFile/WriteFile`, `ReadLine/WriteLine`,
  `ReadInt/ReadFloat/ReadString` and the `Write*` forms, `Eof`, `SeekFile`,
  `FilePos`, `ReadDir/NextFile`, `FileType/FileSize/CopyFile/DeleteFile`,
  `CreateBank`, `Peek*/Poke*`, `CopyBank`, `ResizeBank`, `ReadBytes/WriteBytes`.

The mapping from Blitz constructs to VM bytecode, the planned phases (files,
banks, graphics) and the known differences from Blitz3D are in
`PLANO_BLITZ.md`.

## Bytecode

```bash
./bin/zenblitz --dump game.zbc game.bb   # compile to bytecode
./bin/zenblitz game.zbc                  # run it (no source needed)
```

Types, Data and global initial values are stored in the file; the Blitz
natives are re-registered by the loader.

## Standalone executables

```bash
./bin/zenblitz --build game game.bb          # Linux binary: runtime + bytecode
./bin/zenblitz --build game.exe --stub zenblitz-rt.exe game.bb   # with a Windows runtime
./game arg1 arg2                             # CommandLine$() = "arg1 arg2"
```

Like the original Blitz3D (runtime + program), but with bytecode appended to
the runtime binary instead of x86 code linked into it. The program never
needs the compiler. `--debug` adds per-dimension array bounds checks.

`--build` appends the program to `zenblitz-rt`, the runtime-only executable
next to the compiler (about a third of its size, since it carries no
compiler); `--stub` picks a different one, which is how you build for
another platform. A runtime for a platform is that same `cli/rt_main.cpp`
built there — nothing in the build is host-specific.

## Platforms

`libzen` contains no operating-system calls. Everything a program needs from
the platform — text output, logging, console input, files, directories,
time, dynamic libraries — goes through `zen::Backend` (`zen/backend.h`),
which the host fills in before starting the VM:

```cpp
VM vm;
vm.set_backend(stdio_backend());   // cli/backend_stdio.cpp
install_runtime(&vm);
```

`cli/backend_stdio.cpp` is the console backend (stdio, POSIX and Win32); an
engine plugs in an SDL one instead, and a browser or Android build its own.
Commands that would block — `Delay`, `WaitTimer` — do not sleep: they
suspend the VM with a wake-up deadline (`VM::wake_at()`) and let the host
decide how to wait, so a browser or Android host returns to its event loop
rather than freezing. `cli/host_loop.h` is the console version of that loop.

The library builds in two shapes: `zen_vm` is the runtime alone (what a game
or a web/Android host links), `zen_static` adds the compiler.

## User libraries

Blitz3D-style `.decls` files in a `userlibs/` directory beside the
executable declare functions from a shared library and make them available
as commands. See [userlibs/README.md](userlibs/README.md). Desktop only:
web and Android have no dynamic loading, and calling such a function there
reports it as unavailable.

## Known differences from Blitz3D

- Integers are 64-bit and floats are 64-bit (no 32-bit overflow).
- Very large/small floats print as `1e+10` instead of `1e+010`.
- No IDE/debugger; runtime errors report file and line.

## Source layout

- `libzen/src/bb_toker.*`, `bb_parser.*`, `bb_semant.cpp` — Blitz front-end
  (tokens, AST, type checking, constant folding).
- `libzen/src/bb_codegen.*` — bytecode generation through the `Emitter`.
- `libzen/src/bb_runtime.*`, `bb_cmds.cpp`, `bb_cmds_io.cpp` — Type lists,
  Data, conversions, and the Blitz command set registered as natives.
- `libzen/src/bb_userlibs.cpp` — `.decls` parsing and the call thunk for
  user libraries.
- `libzen/include/zen/backend.h` — the platform services a program needs;
  `cli/backend_stdio.cpp` is the console implementation.
- `libzen/src/compiler.cpp` — `zen::Compiler::compile()` entry point.
- `libzen/src/vm.cpp`, `vm_dispatch.cpp`, `memory.cpp`, `emitter.cpp`,
  `bytecode.cpp` — the VM (about 3 300 lines).
